# PrettyDesk review and test record — 2026-10-01

The local application has undergone source review, regression fixes, real Windows integration checks, rendered WPF inspection, dependency auditing, and an isolated runtime measurement. This is evidence for the tested Windows x64 setup, not a certification of every game, anti-cheat product, display configuration, or release platform.

## Findings corrected

| Finding | Effect before the fix | Result |
|---|---|---|
| Wallpaper backup persistence failure (high) | A failed state save could still permit replacement of the desktop, leaving the original backup available only in memory | Applying now requires a successful durable state save. Failed saves block applying and can be retried without recapturing the replacement wallpaper. Reproduced before fixing; covered by a real Windows regression test |
| Invalid catalog/settings/state graphs (medium) | Valid JSON containing null sections or collection elements could reach dereferencing code | Non-nullable JSON properties and nested collection elements are checked. Invalid local data is preserved as a corrupt-file copy and recovered safely; invalid catalogs are rejected |
| Unbounded signature/download bodies and stalled transfers (medium) | Signature padding, an asset without a declared size, or a response body that never completed could consume resources or occupy download slots indefinitely | Catalogs are bounded to 8 MiB, signatures to 1 KiB, and assets to 8 MiB. Catalog and per-attempt asset transfers have two-minute body timeouts; cancellation and retry behavior have regression tests |
| Duplicate concurrent downloads (medium) | Concurrent dictionary value factories could start multiple writers for the same partial file | Only the winning lazy task starts a download; concurrent callers share its result |
| Epic bootstrapper mismatch and stale launcher records (medium) | Real installed games were missed; stale/add-on manifests appeared installed | Complete Epic entries require an executable launch target and an existing folder. Whole-title matching handles primary manifests whose launch target is a bootstrapper. No substring matching; actual process detection still uses executable rules |
| Launcher scan failure isolation (medium) | One locked manifest or bad library path could hide later games; old Steam library formats were missed | Per-library/per-file failures are isolated, primary Steam scanning survives a locked library list, and legacy library entries are supported |
| ARM64 locked ReadyToRun restore graph (medium) | ARM64 publish failed NU1004 because its x64 crossgen host runtime was missing from declared restore identifiers | The app declares the host runtime for that publish graph. Locked ARM64 publish succeeds without changing package versions or lock contents |
| Misleading security/privacy wording (low) | README claimed no outbound traffic and blanket anti-cheat safety; update comment conflated checksums with authenticity | Copy now describes local game activity and limited process querying. Update integrity checks are distinguished from production release signing |

Details and tradeoffs: [ADR 0008](adr/0008-discovery-and-backup-hardening.md).

## Detection evidence

The read-only real-machine probe found three Steam and three valid Epic manifests, matched catalog IDs `cyberpunk`, `fortnite`, and `rocket-league`, and correctly matched the already-running Rocket League process. It launched no real game and records no process list or installation paths. Before the discovery correction, nine Epic records yielded no installed catalog matches. See [detection receipt](evidence/2026-10-01/review-detection.json).

The catalog contains 46 games and **zero dated verified rules**. This probe proves discovery and the current Rocket League snapshot only. Riot, Battle.net, and Xbox installed-game discovery remains deferred by the spec. Localized Epic titles may require catalog aliases later.

SPEC FR-DET-3 deliberately falls back to executable-only matching when Windows denies a process-path query. Shared executable names, particularly Path of Exile 1/2, can therefore become ambiguous. This behavior was retained to respect the spec; review that policy and test both games before calling their rules verified. No stronger process rights were added.

## Runtime and UI scope

An isolated self-contained x64 acceptance build 1.0.6 ran with the window closed, active Default wallpaper, native detection enabled at the default two-second poll, and the already-running Rocket League excluded from wallpaper switching. It used disposable settings, did not register startup, and scheduled the real Quit handler with restore-on-exit. The measurement completed with 120 samples over ten minutes: **0.023% average CPU, 0.622% peak sample, 63.0 MiB peak private memory**. First/last tenth memory averaged 58.9/61.9 MiB; average handle count changed by -7. This meets the short-run local thresholds, not the 24-hour growth requirement or the required four-core laptop target.

Evidence: [completed sample](evidence/2026-10-01/review-final-idle.csv.summary.json), [CSV](evidence/2026-10-01/review-final-idle.csv), [run scope](evidence/2026-10-01/review-final-run.json). An earlier review sample ended when its timed Quit preceded the sampler's endpoint and is incomplete. The original 24-hour baseline also ended without a completed summary and is explicitly **interrupted**, not passed.

Rendered captures were inspected for Home, Library, Settings, dark theme, and minimum window sizes. No overlapping controls or broken layout were observed in those captures. WPF page smoke tests also ran with the current 32 MiB managed-heap limit. This does not prove native Mica rendering, keyboard/Narrator behavior, high contrast, 300% DPI, or maximum-image stress under that memory setting.

The current build also completed five cached synthetic game sessions through native process detection and the actual desktop COM path: entry **3.757–3.801 seconds**, exit **10.058–10.308 seconds**. Both satisfy the default detect-delay/exit-grace targets for this fixture. This tests the end-to-end detection, grace, orchestration, rendering, and wallpaper application path, not a real anti-cheat game launch. See [switching receipt](evidence/2026-10-01/review-switching.json). Real Quit after both idle and switching runs restored the saved original slideshow sources, options/interval, position, color, and background type: [idle restoration](evidence/2026-10-01/review-idle-restore.json), [switching restoration](evidence/2026-10-01/review-switching-restore.json). Those receipts compare configuration; picture file hash restoration is covered separately by Windows integration tests.

The same original slideshow configuration also matched after the complete Windows test gate: [post-gate restoration](evidence/2026-10-01/review-postgate-restore.json). Both isolated acceptance app processes exited, and their logs contain no error/fatal entries during these runs.

## Security boundaries reviewed

Source and source-guard tests cover limited process information querying, no injection or process-memory reads, per-user startup/storage, non-elevated execution, catalog signature validation before remote parsing, path traversal rejection, asset hashes, corrupt state recovery, and no telemetry implementation. NuGet vulnerability auditing checks direct and transitive dependencies against the configured advisory source. These are scoped checks, not a guarantee against all security defects or a network traffic capture.

The production content URL is still empty, so remote artwork delivery is not released. Loopback HTTPS with a pinned test certificate exercises authenticated catalog download, tamper rejection, and asset verification. Public hosting, real feed access, and production Authenticode signing remain separate release requirements. Signing keys remain outside the checkout; this report includes no secrets.
